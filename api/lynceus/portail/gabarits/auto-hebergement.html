Héberger sa propre instance

Ce projet n'a de sens que si personne n'est obligé de nous faire confiance. Le code est libre : vous pouvez faire tourner votre instance, la modifier, et l'offrir à qui vous voulez.

Pourquoi vous voudriez le faire

  • Aucune clé à demander. Une instance personnelle n'exige pas de clé d'accès. Le contrôle d'accès n'existe que pour protéger une instance publique d'une facture de modèle qui s'envole.
  • Vos analyses restent chez vous. Rien ne transite par ce portail.
  • Votre modèle, votre coût. N'importe quel fournisseur compatible OpenAI convient, y compris un modèle local via Ollama : l'analyse ne coûte alors rien et ne sort pas de votre machine.
  • Votre méthodologie. Les pondérations, le référentiel de procédés et les prompts sont des fichiers {% if depot %}du dépôt{% else %}du dépôt{% endif %}. Vous pouvez en discuter, et les changer.

Le minimum vital

Avec Docker, une instance d'essai tient en une commande, sur SQLite, sans base à installer :

git clone {% if depot %}{{ depot }}.git{% else %}<dépôt>{% endif %} lynceus && cd lynceus/api
cp .env.example .env        # y placer la clé du fournisseur de modèle
docker compose up -d

Pour une instance destinée à d'autres personnes, {% if depot %}le dépôt{% else %}le dépôt{% endif %} fournit un docker-compose.prod.yml (PostgreSQL, migrations automatiques, exposition par Cloudflare Tunnel) et un guide de déploiement détaillé, y compris la façon d'estimer la dépense avant d'ouvrir les portes.

La règle à ne pas oublier

Une instance exposée sans clés d'accès permet à n'importe qui de dépenser votre argent : chaque analyse appelle un modèle facturé à l'usage. Le compose de production refuse d'ailleurs de démarrer sans clé publique configurée. Ce n'est pas de la prudence excessive, c'est la première mauvaise surprise qui guette.

Portail et instance sont deux choses

Ce que vous lisez est un portail : il présente le projet, distribue l'extension et délivre des clés. L'instance, elle, analyse et stocke. Elles sont volontairement séparées, parce que le portail détient la clé privée qui signe les clés d'accès : si l'instance était compromise, personne ne pourrait pour autant émettre de clés en votre nom.

Un même portail peut d'ailleurs délivrer des clés valables sur plusieurs instances. C'est la première pierre de ce qui deviendra un réseau d'instances fédérées, plutôt qu'un service central de plus.

Contribuer

La discussion la plus utile ne porte pas sur le code. Elle porte sur le référentiel de procédés, sur les pondérations, et sur les cas où l'analyse se trompe. Ces fichiers sont publics précisément pour être contestés.
